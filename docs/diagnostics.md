# Local diagnostics

Diagnostics connects launcher actions, setup stages, runtime requests, and browser operations through OpenTelemetry trace and span identities. It is local-first: no monitoring server, network-accessible diagnostics endpoint, or remote exporter is required. Diagnostics records provide evidence and allowlisted links to existing recovery workflows; they do not authorize setup changes or retries.

The launcher continues checking its managed tunnel every ten seconds. Adopting an already-ready tunnel first resolves its verified loopback health endpoint so routine monitoring can use local HTTP checks; if that optional locator is unavailable, the monitor retains its bounded native inventory fallback and reports the discovery gap. Once monitoring is active, a successful local tunnel inventory control command retains its full process lifecycle at most once per five minutes; repeated healthy controls do not fill the diagnostic store. A failed control still records its typed cause, process and output-drain evidence, with buffered child observations labelled by their original elapsed time. Tunnel readiness transitions and monitor failures remain separate events. A sampled healthy control proves only that observed instant, not uninterrupted health between samples.

## Architecture and build

The authored implementation is strict TypeScript. Shared Zod contracts in `src/diagnostics/contracts.ts` validate records, queries, capture commands, problem envelopes, and worker messages. The root compiler targets Bun; the renderer and Electron diagnostics compiler configurations are separate. `scripts/build-diagnostics.ts` emits the CommonJS host adapter and preload consumed by Electron. Generated JavaScript is not a second implementation.

`Diagnostics` uses explicit OpenTelemetry tracing and logging providers with local exporters, without registering a remote/global SDK. Producers preserve supplied task identifiers and names, but do not scrape conversation titles or derive names from prompts. Command results remain on stdout; launcher-owned child diagnostics travel on a separate inherited pipe. Standalone processes use the same bundled Bun worker implementation.

The shared browser-helper client captures the submitting task's asynchronous context and restores it when dispatching that task's callbacks and cleanup. A shared pipe's creation context does not establish task ownership. This keeps deferred prompt preparation, broker registration and lifecycle records correlated with their originating HTTP trace during concurrent work.

SQLite work runs outside the Electron renderer/UI thread. A separate query worker executes searches with a two-second limit and is terminated and joined on cancellation or timeout. WAL, FTS5, indexed filters, and sequence-based cursors support concurrent writers and paginated read-only access. Follow cursors advance by ingestion sequence rather than producer clocks, so late-arriving events are not silently skipped. Background capture-state polling waits until the client has no pending worker request, preventing a poll's shorter deadline from retiring a worker occupied by another bounded operation. Explicit requests retain their own deadlines.

Retained legacy logs import in the background after worker readiness, in batches of at most 128 records with an event-loop yield between batches. Deterministic record identities make interruption/resumption idempotent; storage failures do not mark a file complete. Unfinished imports remain visible to read-only queries across restart. Shutdown cancels and joins the importer, and clearing normal records is refused during an active import so backfill cannot immediately repopulate a cleared store. Routine WAL flushing uses SQLite's configured automatic checkpoint threshold; explicit reclamation runs when the complete database/WAL budget requires it. The original log files are not changed by import.

Schema version 2 keeps sanitized events authoritative. The span projection selects terminal evidence over delayed starts. Trace membership counts, problem codes/recovery state, and operation-duration metric samples are maintained transactionally and removed with their underlying events. Opening a version-1 store with the writer adds these projections without replacing its records. Unsupported schema versions fail closed; read-only access does not upgrade a database.

Schema version 5 adds a covering index for per-campaign and global content-byte totals. Capture admission checks these totals inside its write transaction; the index avoids reading captured-text pages for each check. Migration preserves the captured content and its identifiers, hashes, scope, and limits. It does not change lock-wait or worker-request deadlines.

Worker bootstrap failures use a bounded private-transport response before any request is accepted. Clients preserve the startup phase and recognized SQLite lock subtype for pending and subsequent requests, while status reports the unavailable collection. Raw exceptions and database contents are excluded. A startup failure does not restart the worker or replay a request.

Stores live beneath the selected application's data directory at `diagnostics/observability/diagnostics.sqlite`; development and production use their existing separate data roots. Target/profile identity remains attached to records and available as a filter. Paths, subprocess invocation, export replacement, and Electron dialogs are isolated from presentation components. Runtime bundles carry Bun and the query worker; diagnostics does not require a system Bun, Bash, Unix socket, or external database.

## User workflow

Overview shows recent problems/interrupted operations, a read-only runtime health observation, and separate collection status. Operations presents named operations and an expandable correlated stage timeline. Advanced provides event filters, full-text/regex search, paging, technical details, and pause/resume controls. Capture & storage contains debug/private controls, retention, storage usage, deletion, and sanitized export. A failed launcher action carries its observed owning trace into the notice when one exists, so Open Diagnostics selects the corresponding operation timeline; a structured child trace remains its own owner.

The workspace and capture indicator share one diagnostics controller. Health/capture observation continues while automatic list updates are paused. Foreground search is debounced by 180 ms and exposes its reserved progress/cancellation control only after 300 ms; background refresh never uses that control. Each request has an independently cancellable renderer-owned identity. Superseded responses cannot replace newer results. Selection, expanded groups, and older-scroll inspection hold automatic list replacement and expose a New activity action instead.

Overview groups operation occurrences, not propagated error records. The first chronologically recorded problem represents an occurrence; this is a presentation rule, not an inference that it is the ultimate cause. Its code, stage, component, target, and runtime version identify a repeated signature. Ambiguous generic failures remain separate unless their application-owned message identifies a known producer. Occurrences are newest-first, while correlated stages are oldest-first. Advanced and operation reports preserve every retained raw record. Historical cancellation/error contradictions are explained without rewriting evidence or inventing a cancellation reason.

ChatGPT errors retain their observed source. A dismissible request-frequency dialog is recorded as a `chatgpt-ui` notice and does not claim an HTTP 429 or account exhaustion. The owning browser stages dismiss that known notice before privacy-gated checkpoints; an unknown or authentication dialog remains excluded from capture, and post-completion dismissal cannot revoke an already completed answer. A dialog that cannot be dismissed before Send becomes a typed UI failure, with ownership recorded when the message was never sent. The owned main-frame conversation POST separately classifies HTTP rejections and transport loss; only its actual HTTP 429 is a provider rate-limit observation. The inspector shows the problem source, code, HTTP status when present, and related typed causes without copying dialog text, credentials or response bodies. A later successful owned POST can supersede an earlier failed attempt within the same browser turn; uncertain transport outcomes are never replayed automatically.

Launcher action feedback has an explicit policy for every API member: navigation, subscriptions, and ordinary state reads stay quiet; work-producing controls share admission, pending state, and completion feedback. Consecutive identical pending requests share one execution; differing requests to one launcher API method execute in order. Group and timeline work have separate admission scopes. Feedback shows a compact latest-result notification in the lower-right corner without a full-width bar or shrinking the workspace. Details expands the selected operation's findings, causes, recovery state, available stage/time information, and applicable actions. History is a separate control; simple successes without additional evidence have no Details button. Transient history keeps the latest 50 notices plus pending and currently inspected notices; durable operation evidence remains in Diagnostics. Incoming notifications do not replace the inspected operation. Escape restores focus to the available notification control, and an outside click closes the expansion. The global notice overlay is hidden while Diagnostics is the active surface so its inspector and filters remain unobstructed; the notice controller and dismissal timers remain mounted, and notices reappear when leaving Diagnostics. Dialogs display only explicitly scoped feedback from operations started in that dialog, never unrelated global notifications.

Operation events enrich the corresponding API-owned notice rather than making an intermediate stage look like completion. Application-owned structured problems cross IPC and contextBridge as validated plain results before the renderer reconstructs an error; raw subprocess output is not treated as a problem contract. Accepted launches/updates are distinct from verified completion. Explicit cancellation is neutral; a genuine recorded failure preceding cancellation remains a failure. Setup review cancellation does not emit an unexpected-error problem. Startup preserves configuration conflicts and offers review without automatically attempting route restoration. A genuine runtime failure may still require recovery, whose result is correlated with the original startup operation. Runtime availability is recorded separately from integration readiness. See the [September 6 relaunch investigation](relaunch-errors-2026-09-06.md) for the observed error families and the limits of historical evidence.

Embedded browser views retained offscreen must follow the current native window geometry while Diagnostics or another launcher surface is active. The host coalesces resize placement after native bounds settle, because Electron/X11 can emit a resize event before reporting the new content size. Pending placement work is cancelled when the browser host is destroyed; no renderer-mounted browser slot is required for this update.

Treat outcomes literally: a recorded failure is not proof that rollback failed, and missing terminal evidence is not success. Running is a last-observed state, not a process-liveness assertion; queries disclose stages without terminal records. An observed abnormal child exit records interruption for its unfinished stages, while a clean exit without completion evidence records an unknown outcome. A whole-launcher crash may leave only the original start evidence. Structured problems preserve stage, findings, causes, correlation, and observed recovery state. Stale setup previews require a fresh review; refreshing a preview invalidates its previous checkbox approval. Existing setup workflows continue to own exact-preview approval and configuration changes.

## CLI and agent interface

Use the installed runtime command, followed by any existing global target-selection options and `diagnostics`. For source development, the equivalent prefix is `bun run src/cli.ts`. Examples below use `codex-chatgpt-web` as the installed command name.

```text
codex-chatgpt-web diagnostics status --json
codex-chatgpt-web diagnostics list --view operations --limit 100 --json
codex-chatgpt-web diagnostics show TRACE_ID --json
codex-chatgpt-web diagnostics search "preflight" --component launcher --json
codex-chatgpt-web diagnostics search --regex "preview|recovery" --json
codex-chatgpt-web diagnostics follow --trace TRACE_ID --json
codex-chatgpt-web diagnostics export --output report.zip --format bundle
```

`status`, `list`, `show`, and `search` are read-only and work with the launcher closed. They do not start the bridge or apply configuration. `show` requires a valid trace identity. `follow` polls until interrupted; its output is newline-delimited versioned query results. Ordinary JSON query responses contain `version`, `events`, `incomplete`, `notices`, and optional cursors. Reuse a page cursor with the same filters. Filters include target, component, severity, task, trace, and time bounds; `diagnostics help` is the argument reference. Collection unavailability is represented explicitly in `status --json`, not as a healthy empty store.

Agents and users retrieve the same retained records. Inspect notices and completeness before drawing conclusions. A diagnostic problem can suggest review or Doctor, but execution still needs the authority of the originating workflow. Export is an explicit local write to the chosen path, not a transmission. Clearing and capture activation are separate confirmed controls, not side effects of reading evidence.

## Bounds, privacy, and portable reports

Normal retention is 14 days or 64 MiB, counting the SQLite database, indexes, WAL, and shared-memory file. Expired records are pruned when a writer opens and during maintenance. Retention removals are disclosed separately from collection drops. Read-only queries exclude expired evidence without mutating storage. A paused or closed application cannot perform physical cleanup until its writer runs again.

Producer event queues and outstanding request bytes each have a 4 MiB budget. Records are capped at 12 KiB after sanitization; batching is limited to 128 records, pages to 200, and worker requests to 2 MiB. Failures and span lifecycle records take priority over repetitive lower-priority events. Status and capture-state reads wait for pending requests to settle before sending worker input. Admission waits are bounded by ten seconds during cold startup or two seconds afterward; an occupied worker produces an explicit busy result without retiring transport or claiming a healthy collection. Once admitted, the read has its own execution deadline of the same length. Writes and exports keep their existing deadlines. At most 32 health reads may wait for admission, and cancellation removes a waiting read without sending it. Before retiring a timed-out worker, the client allows pending I/O to drain so a synchronous parent pause cannot discard an already-written response. Unanswered requests still retire transport, with the method, deadline, elapsed time and pending request count retained. Payload-free worker request-start records let timeout notices distinguish started operations from requests whose worker start was not observed; write progress also identifies validation, transaction and commit work, with retention progress for appends. These records neither establish completion nor permit replay. Worker shutdown records its reason, and an unexpected exit retains process identity, exit code and signal without collecting raw worker stderr. Termination closes the input stream even if its parent leaves the pipe open. Collection failures are reported without changing the task's result.

Debug activation lasts 30 minutes and captures additional structural evidence only. Normal/debug records exclude prompts, responses, credentials, raw browser DOM, and screenshots. A private browser-capture session requires explicit acknowledgement and an operation scope, lasts at most 30 minutes, and has a persistent launcher indicator. A next-turn scope is claimed by exactly one trace. Authentication/settings/embedded-frame surfaces are excluded by a conservative browser gate, which is checked again after capture. Each accepted PNG is at most 1 MiB and is stored separately with owner-only creation permissions on POSIX. Private files expire after 24 hours and have a separate 128 MiB budget; cleanup runs on worker opening and maintenance. Stopping a session revokes further admission, but deletion is a separate control.

Independent producers refresh capture/debug controls every five seconds; inactive checkpoints do not wait for a status query. An active capture rechecks its scope before taking an image and again on persistence, so a stale local activation cannot authorize storage. Additional visible input controls are excluded even when their HTML type is generic. The private store admits at most 1,024 files, reports missing/expired files, and confirmed deletion removes owned UUID-named orphan images without deleting unrelated files.

Ordinary copy/export excludes private files, local task names, identifying home paths, and sensitive attributes. Export formats are JSON, self-contained HTML, a ZIP support bundle, and OTLP JSON. The bundle contains the HTML report, sanitized JSONL records, component versions/collection health in a manifest, and standard OTLP trace/log documents. HTML has no external assets or scripts, escapes record content, and remains usable without Electron. Exports are capped at 20,000 records or approximately 32 MiB of record JSON; the report discloses an incomplete selection. Destinations cannot alias the store/private directory, and replacing an export does not alter permissions on its parent directory.

An isolated synthetic campaign can explicitly acknowledge scoped content capture, bind its traces, and retain prompts, outputs, tools, transport, oracle evidence, visible conversation state, and conversation screenshots. Authentication surfaces and credential content remain excluded; unsupported or oversized content produces an omission rather than silent truncation. Text scrubbing preserves noncredential JSON numeric and whitespace lexemes. A campaign admits at most 10,000 attachments, each bounded to 1 MiB of UTF-8 text, with a default 512 MiB campaign budget and a 1 GiB global content limit. Active campaign traces remain pinned against ordinary retention; confirmed private deletion removes campaign content as well as private images. Retention reclaims reusable database pages before deleting unrelated events to meet its physical-size budget.

Larger text documents use the same worker's bounded document-transfer interface: start, ordered parts, then finish or abort. The document limit and aggregate declared input budget per worker are 64 MiB, with at most eight receiving documents and a 60-second inactivity lease. Partial raw content stays in memory; only transfer identity, declared byte count and receiving state are durable. The regular worker maintenance sweep releases expired fragments and marks their document omitted even if no later capture command arrives. The worker inspects the whole document before storing its sanitized chunks in one transaction, so credentials spanning transport parts remain protected. A crashed or interrupted transfer remains visibly incomplete after restart and cannot silently resume from missing memory. Both ends of the worker transport decode UTF-8 incrementally, preserving characters split across pipe reads. Schema four adds document metadata while retaining earlier capture evidence.

Content-inclusive bundles require the campaign ID and explicit acknowledgement. They include the entire campaign snapshot at export start, independently of the diagnostic record selection, with attachment identities, encodings, hashes, document/chunk identities, and omission counts in `content/manifest.json`. Reconstruct a stored document by joining its chunks in `document.index` order; its document byte count and SHA-256 describe the sanitized complete text. Export verifies both the individual attachments and each complete document. Attachments are read, verified, compressed, and written incrementally so every admitted campaign has an export path beyond 64 MiB. The destination is replaced only after the complete temporary bundle is written and synced; missing or corrupt attachments or documents fail the export. Open campaigns, unfinished documents, recorded collection failures, and persisted omissions make the export incomplete. Diagnostic filters do not hide collection failures for traces bound to the selected campaign. The ordinary reports inside the bundle remain sanitized; the separate `scopedContentIncluded` field identifies the additional sensitive campaign evidence.

Schema six records each new campaign's ingestion sequence and lifetime reported-drop counter in the same transaction as capture start, and records its closing boundary at finish. Repeated finish calls preserve that boundary. Legacy campaigns retain their content with an unknown boundary; migration does not invent historical counters. Producers settle and flush before finish, since these counters cannot measure loss that was never reported. The lifetime counter remains cumulative.

A bundle containing an explicitly selected campaign can measure reported loss over that campaign's recorded interval only when every selected diagnostic trace is bound to the campaign and its selected records were ingested within that interval. Mixed, unscoped and out-of-interval selections retain the lifetime loss assessment. The report keeps both the lifetime counter and the applied scope boundaries visible. Unknown boundaries, new reported drops, omissions, incomplete transfers, missing records and collection failures remain incomplete evidence; a zero-drop interval does not establish a task outcome. Late evidence outside a finished interval cannot be attributed to that interval on re-export.

Copy and Export menus expose the applicable event, operation, and current-results scopes; all retained diagnostics is an explicit export scope. Copy supports a readable summary or JSON and is bounded to 1,000 records or 256 KiB of compact record JSON before formatting. Both paths use the same worker-owned report assembly and sanitization. Results cover all matching pages, not just the loaded page. A sequence boundary freezes selection before the export chooser opens. Returned metadata identifies record count, incomplete evidence, and the saved destination; chooser cancellation is not success. Correlation identifiers, timestamps, and component versions remain, so these reports are not anonymous.

The native save dialog suggests a sortable UTC timestamp, for example `codex-web-gpt-diagnostics-2026-09-06T04-52-31-247Z.json`. The `T` separates date and time; colons and the fractional-second separator become hyphens for cross-platform filenames. Milliseconds distinguish nearby exports, but are not a global uniqueness guarantee. The user still chooses the destination and confirms replacement through the native dialog.

## Reproducible storage measurements

Run `bun run scripts/benchmark-diagnostics.ts` with the pinned runtime. It uses synthetic data in disposable stores, one closed-loop writer with batches of 128, thirty warm indexed queries per dataset, and one fresh-worker query per dataset. Generation time is excluded from ingestion time. Its output distinguishes offered, accepted, retained, retention-removed, and dropped records, and includes storage bytes and sampled peak writer RSS. This is a storage measurement, not an Electron responsiveness or open-loop saturation claim.

On Linux x64 / AMD Ryzen 9 3900X / Bun 1.4.0, the September 5, 2026 run after retention reporting produced:

| --- | --- | --- | --- | --- | --- | --- | --- |
| Default 64 MiB budget | 30,000 / 30,000 | 27,952 | 66,081,888 | 9,346 | 3.76 ms | 83.82 ms | 105,324,544 bytes |

The Chromium renderer fixture loads 1,000 synthetic records while mounting at most twelve list rows. Ten Playwright End-to-last-record-focus samples measured 5.02–10.73 ms, with 11,372,904 bytes of JavaScript heap reported by Chromium. The renderer is real, but its API is synthetic; these measurements include test-driver overhead and are not physical input-latency or whole-process memory guarantees. The whole-launcher fixture separately connects the real emitted host, worker, SQLite and CLI through a test-only substitute for Electron IPC. A UI-visible synthetic failure is independently retrieved through the CLI; this is not a reproduction of the user's original approval failure.

During an explicitly scoped synthetic campaign, the broker retains completed tool arguments and multimodal replies through the production content-capture interface under the original invocation context. The native result is delivered even when capture fails; the campaign records that missing evidence and cannot pass acceptance. Outside that scope, ordinary tool diagnostics retain stage and correlation metadata without tool bodies.

Broker tool spans retain the exact invocation identity when cancellation ends a pending call. A termination attribute distinguishes authenticated native interruption and proved same-turn steering supersession from an unclassified abort. This records why the broker ended the invocation; it does not claim that a native side effect completed or that a tool result was returned.

Browser evidence capture preserves running animations. Disabling animations can fast-forward their finish handlers and mutate application state, so capture observes the rendered frame without forcing animation completion. Post-capture validation reports its stage, a fixed exclusion reason, and whether navigation changed; discarded images remain unpersisted.

Worker request failures retain payload-free request metadata: method, content action when applicable, observed write phase, and client-observed elapsed times. Event appends and content captures distinguish validation, transaction work and commit; appends also identify retention work. Recognized SQLite lock codes and numeric extended errors survive the worker, Electron result bridge, and correlated problem findings. Campaign capture and omission failures report those typed problems through the ordinary collection sink independently of the content worker, retaining the scope's failure marker for acceptance. A stale snapshot has a distinct failure code; a generic lock rejection does not establish another writer's identity or how long it held a lock. Neither failure permits automatic replay of an uncertain write. Raw database messages, SQL, request bodies, and worker stderr are excluded from this error contract.
