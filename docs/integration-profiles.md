# Integration targets and independent CLI profiles

Settings presents the current **Codex connection** independently of profile enumeration. Most users need only that connection. **Advanced: separate command-line profiles** exposes existing targets and guided creation with the current Codex home and an unused `chatgpt-web` name preselected; folder selection remains an advanced option. Opening the new window does not install anything: capability checking and the existing configuration approval still precede installation.

Read-only discovery reports available, externally managed, unavailable, and unsupported entries separately. Linked profiles show **Managed elsewhere** and their resolved location without granting write ownership. A broken link or optional registry entry does not blank the current connection. Doctor treats valid external links as informational and optional failures as warnings. Edit-time target resolution still rejects links, including broken links; discovery never replaces them or redirects the Codex home. Platform capability gates remain unchanged.

The desktop-wide base integration remains supported. A base-routed Codex session depends on the bridge, including when it selects a native OpenAI model: native requests are authenticated passthrough, not transparent per-model desktop bypass. An unintegrated base configuration can run native Codex independently while named bridge profiles are stopped. This application does not replace your `codex` wrapper or change which profile the Codex desktop app launches.

A target identifies a canonical Codex home, either `config.toml` or `<name>.config.toml`, and one owning runtime home. Profile names use 1–64 ASCII letters, digits, underscores, or hyphens. Symlinked configuration aliases and path traversal are rejected. The base runtime retains its existing directory and restoration journal. Named profiles use `<runtime-root>/targets/<target-id>/`, with separate runtime settings, journals, model catalogs, logs, control tokens, broker endpoints, launcher data, and persistent browser partitions. The target ID includes the Codex home, so equal profile names in different homes are distinct. One legacy base runtime cannot be reassigned to another Codex home while it retains that home's ownership evidence.

The launcher’s Settings → Integration targets opens or focuses a target’s own window. Opening another window does not stop the current one. Existing profile files are listed without acquiring ownership. Each profile needs its own explicit browser sign-in and, for Full mode, its own tunnel and connector setup. Default Automatic and Zero Risk connector names include a target-specific suffix. No browser sessions, runtime keys, or credentials are copied from another target. Profile windows do not alter the base launcher's login-item setting. macOS daemon and tunnel labels are target-scoped; native Windows/macOS service and installer acceptance must still be run on those operating systems.

## Capability gate and launch commands

Named-profile support is gated on the actual Codex CLI executable, not a version-number guess. The offline probe tests precedence, profile-local catalog loading, shared native-cache preservation, launch behavior, and positive/negative Interrupt trust identity using disposable fixture homes. It does not submit a model message or use your authentication. The current hook probe requires Linux and `/usr/bin/script`; profile installation on Windows and macOS remains blocked until equivalent capability probes are available. Linux `codex-cli 0.153.3` is the currently exercised binary family; every selected binary still needs its own successful receipt, bound to its absolute executable path, bytes, and platform. Updating or replacing it invalidates that evidence. A missing capability blocks profile installation rather than falling back to global settings. Select the raw executable, not an interactive shell wrapper.

```sh
bun run src/cli.ts --codex-home /absolute/codex-home --codex-profile web-native targets check --codex-binary /absolute/path/to/codex
bun run src/cli.ts --codex-home /absolute/codex-home targets list
bun run src/cli.ts --codex-home /absolute/codex-home --codex-profile web-native targets inspect
```

`targets check` also reserves the profile's stable local port. The registry serializes reservations, excludes the base port and peer reservations, and never silently reassigns an occupied existing reservation. An unexpected listener requires ownership inspection. `targets inspect` and the launcher expose the exact launch command using the verified executable, `CODEX_HOME`, and `--profile <name>`. Start that profile's bridge before launching Codex. Commands without target selectors retain base behavior; profile launchers pass explicit selectors to their configuration children.

Setup, `route`, `route repair`, `subagents`, Doctor/status, and uninstall accept the target selectors. CLI profile setup uses its reservation; an explicit `--port` must match it. Setup still requires the same exact review and browser/tunnel prerequisites as the base workflow; target selection is not approval to modify an existing file. Linux and Windows use the launcher for managed browser setup. The `serve` command runs the selected configured runtime in the foreground.

## Model metadata and inheritance

Profiles set their own `model_catalog_json` and the OpenAI provider, with restoration baselines for existing values. The shared native `models_cache.json` is read-only input for profile operations. If it is missing, unusable, or already contains bridge-augmented rows, catalog generation reads bundled metadata from the verified binary in an isolated home without authentication. In particular, a cache previously pinned to Compatibility V1 by the base bridge is not mistaken for an untouched native catalog. The application augments current native metadata, retains native model ordering, applies the selected protocol, and respects layered `model_context_window` configuration.

The profile catalog refreshes at runtime startup, when health/request checks detect changed inputs, and through `targets refresh-catalog`. Invalid inheritance, capability evidence, or metadata makes the profile report unavailable catalog readiness and reject new routed work; it does not stop existing turns or repair user configuration automatically. Health distinguishes a ready generated file from proof that a Codex process loaded it. Restart or relaunch the selected Codex profile after configuration/catalog changes; there is no claim that an already-running Codex process hot-reloaded the file.

Base and profile assignments are separate layers. A profile override is not an invalid duplicate. Hooks are additive, however: a profile cannot override away a base Interrupt hook. Installing another bridge hook while one is inherited is blocked. Unrelated hook arrays are preserved and never deduplicated. These behaviors follow the current [Codex profile configuration](https://learn.chatgpt.com/docs/config-file/config-advanced) and [hook loading model](https://learn.chatgpt.com/docs/hooks), with the executable probe providing local capability evidence.

## Reviewed base-to-profile migration

Open the destination profile window, complete its capability check and explicit browser prerequisites, then choose **Review base-to-profile migration**. Quit the base launcher and stop any externally managed base service through its owner first. CLI callers add `--migrate-base` to both the setup preview and the approved setup invocation. Migration is never automatic and cannot apply without the exact preview approval.

The combined preview shows both targets and both source diffs. It restores only base routing, protocol settings, and the exact owned Interrupt hook that still match the base journal, preserving newer user values and unrelated hooks. It installs the destination profile in the same compensated configuration transaction. Version 10 active base ownership is required; missing, conflicting, or older restoration evidence remains a blocker. Hook removal that would invalidate later user-hook trust indexes also remains blocked.

Original primary/recovery journals are archived privately under `<base-runtime>/codex/migrations/<digest>/` before the active base journal copies are removed. A receipt records source/target identities and before/after hashes, not a copy of the full Codex configuration. The destination captures its own prior profile baselines. The base runtime settings and browser state are left alone. Migration checks the base endpoint before setup effects and again before applying configuration; a listening endpoint prevents application. A closed port is necessary evidence, not proof that every external process has stopped—keep the base owner closed during review and apply.

## Interrupt cleanup and recovery

The Interrupt hook requests cleanup for one exact Codex session and turn. It is not message interception. Its executable, event, three-second hook timeout, and changed trusted definition are shown in review, with exact commands and hashes in expandable details. The authenticated control request is bounded to two seconds. Cancellation received before request registration remains authoritative through the runtime's interruption tombstone.

Control acknowledgements distinguish completed, pending/failed, and armed-before-registration cleanup. A normal hook exit is not evidence that browser work stopped. Runtime-owned requests create minimal private unresolved-work receipts under `runtime/interrupt-cleanup/` before dispatch; filenames hash session/turn identity and contain no prompt or raw identity. Successful HTTP work releases its receipt only after matched browser/compaction settlement; errors and disconnects retain uncertainty. Interrupted or crashed work retains uncertainty until the owning runtime confirms cleanup. A new idle runtime does not erase old crash evidence. Unavailable bridges are quiet for unrelated turns; recorded exact-turn work receives a targeted warning. Pending physical teardown can also produce a warning while cleanup continues. Structured-compaction cancellation remains conservatively unconfirmed when its terminal outcome cannot distinguish expected cancellation from cleanup failure. Inspect that target's runtime/browser before removing unresolved evidence manually; do not infer success from the absence of a running listener.

Configuration writers lock overlapping files and recheck preview inputs before mutation. Another file, target, protocol, resolution choice, or output invalidates approval. Failed writes compensate only bytes still owned by that transaction; external edits are not overwritten. Stale `.cgw-write.lock` or registry lock files require inspecting their owner and the configuration/journals before manual removal. These are cooperating-writer locks and guarded compensation, not operating-system compare-and-swap or crash-proof multi-file transactions. After a crash or a later launcher startup failure, inspect both targets and archived evidence before restoring anything; do not copy old runtime/browser snapshots over newer state.
