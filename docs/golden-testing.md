# Native golden testing

The golden catalog in `scripts/golden/catalog.ts` derives automatic routes from the production model catalog and an explicit account capability snapshot. It retains the full compatible product of workload, effort, protocol, scenario and execution lane, with separate exclusions and an assisted Zero Risk lane. Pro generation remains prohibited until the campaign owner separately authorizes it after non-Pro acceptance. Creating the catalog or passing a driver test does not establish live matrix acceptance.

The Linux hidden-workspace launcher requires `CODEX_WEB_GPT_ELECTRON_EXECUTABLE` to name the reviewed patched Electron binary and `CODEX_WEB_GPT_ELECTRON_BUILD_RECORD` when its build record is not beside that binary. It verifies the binary hash before creating a display, then passes the same record to the isolated launcher. Stock `node_modules/electron` is not a golden runtime. The ordinary package and native Windows/macOS acceptance remain separate.

`workloads.ts` supplies the same generated reconciliation inputs and prompt contract to every effort. Its artifact oracle uses independent integer arithmetic, validates immutable inputs and requires a separate dataset for reusable project verification. The durable SQLite queue contains scheduling state only. It retains uncertain running attempts across restart and refuses to pass cells without artifact, commit, settlement, diagnostic, variant, model/effort and duplicate-effect evidence. Level five additionally requires at least two hours of evidenced active progress.

The `formats` scenario adds the full PDF, DOCX, XLSX and PNG fixture set at every level, alongside the shared text, Markdown, JSON and CSV inputs. The native exec driver performs one task; the independent oracle checks extracted document references, the visual two-digit code, transformed JSON and CSV, and unchanged source files. Format coverage has a distinct workload identity and cannot accept an ordinary level-one workload without its attachments. These are native file/tool interpretation checks; they do not establish browser-upload compatibility for every document type. Level-five execution still requires the sustained coordinator and progress evidence.

## Native interfaces

`exec.ts` invokes `codex exec --json` with an explicit route, effort, provider and workspace sandbox. Resume uses the exact captured task UUID. Prompt capture and process ownership are established before stdin submission. Completion requires a terminal native event as well as a successful process exit; cancellation, missing terminal evidence and deadline expiry cannot trigger an automatic replay.

`app-server.ts` uses the installed native JSON-RPC interfaces for Plan mode, steering, interruption and subsequent turns. It matches both thread and turn identities, retains completion that arrives before the start acknowledgement, rejects stale action targets and keeps uncertain submissions unresolved until terminal evidence is observed. The underlying RPC client records bidirectional frames, rejects malformed transport and prevents a delayed capture callback from submitting a request after its deadline. Batch admission first initializes the shared native home through an initialize-only app-server process and waits for it to close. This keeps task submission behind observed initial-home readiness without changing the shared history-authentication boundary or creating a generation; subsequent startup can still fail and must provide its own readiness evidence. Initialization has a separate 90-second bound for cold native startup; ordinary request acknowledgements retain their 30-second deadline. Native protocol failures use the shared structured diagnostic error contract and cannot authorize automatic replay. An observed process exit retains its exit code or signal; raw native stderr remains separate scoped evidence.

`tui.ts` creates a private tmux socket and a separate native app-server control socket, then connects the native terminal through `--remote`. It does not attach to a desktop app or a shared terminal. Readiness must be established from the loaded model and actual UI state: the initial placeholder and a slash-command suggestion are insufficient. The driver explicitly pins `plan_mode_reasoning_effort`, because the native `/plan` action otherwise defaults to medium effort. The native terminal can also issue a separate task-title request; this is additional provider work and belongs inside admission accounting and scoped capture.

Both JSONL drivers share one owner for detached process groups, stream settlement and bounded shutdown. The TUI driver additionally verifies its tmux socket inode and native pane/process identities. Terminal snapshots are selected UI observations; they do not replace the production bridge's full response and tool capture.

`native-socket.ts` lets the same RPC client observe the exact private TUI endpoint over a Unix WebSocket with compression disabled. Attachment and sends check the canonical private directory, endpoint inode and native process identity. Frame size and queued capture are bounded, request deadlines fence delayed sends, and closing the observer leaves the owning app-server running. Main task turns can be read through the native thread interface. Ephemeral title tasks expose global lifecycle notifications but do not expose the same retained turn history; their identity and provider settlement need separate evidence.

Current installed native app-server releases can publish a private symlink at the requested endpoint and hold the listening socket under a separate user-owned mode-700 directory. The TUI observer accepts that shape only when the link and target identities stay fixed and the recorded app-server process holds the exact listening socket FD; a link to another process or a replaced link fails ownership checks.

Both sides of the TUI connection receive the same explicit model, provider and effort configuration, including Plan effort. Readiness checks the latest loaded model row; an older loading banner can remain in scrollback. Artifact execution passes the canonical disposable repository's Git directory as an explicit writable root. The native toolchain fixture exercises exec, app-server and TUI outside the system temporary directory, where implicit temporary-directory permissions cannot mask a missing grant, and checks that a sibling repository remains inaccessible.

`tui-scenarios.ts` submits the shared workload in Plan mode, reads the resulting native task and Plan items, accepts the terminal's execution choice, and observes the subsequent completed turn. It retains native process identities, terminal inputs and snapshots, socket frames, plan hashes and separate ephemeral title lifecycles through production campaign capture. A title's `systemError` frame is retained before observation stops with `native_tui_title_failed`; timer cancellation preserves that typed failure. Transport failure cancels outstanding observation; an uncertain input is never replayed. The live owner separately requires title HTTP completion, observed model/effort and correlated shared admission/release records. Native idle alone does not establish title-generation success.

Helper lifecycle requests propagate their active diagnostic parent through the authenticated launcher control channel. Admission retains that context with each entry, so deferred acquisition or release triggered by another task cannot change attribution. Scoped structural queries can suspend admission on a correlated title rate limit even when campaign content is incomplete; that query path cannot establish acceptance. The native rate classifier recognizes both the explicit rate-limit variant and the observed exhausted HTTP-429 variant, without matching message text.

An observed title failure carries its native task identity through cancellation and aggregated cleanup errors. The batch includes that identity in its ancillary admission query even when the TUI scenario never returns successfully. A `systemError` by itself is not classified as a rate limit; a matching scoped provider record is required before persisting an admission hold.

## Controlled local verification

Set `CODEX_TEST_PROFILE_BINARY` to the installed native executable to enable the optional consumer tests. Use the repository's pinned Bun runtime when the shell's `bun` resolves elsewhere. For example, from the repository root:

```sh
CODEX_TEST_PROFILE_BINARY=/usr/lib/chatgpt/resources/codex \
  launcher/build/runtime/runtime/bun test \
  tests/golden-native-protocol.test.ts tests/golden-app-server.test.ts \
  tests/golden-exec.test.ts tests/golden-native-consumer.test.ts \
  tests/golden-tui.test.ts
```

The native consumer fixtures bind a loopback-only provider in a disposable Codex home and return deterministic output through the production Responses bridge. They neither sign in to ChatGPT nor call a model provider. The fixtures exercise native exec completion and resume, streamed Plan delimiters after HTML conversion, plan revision, interruption followed by execution, local browser-failure classification, and the real terminal's plan implementation action. The terminal fixture checks requested effort and process settlement. These controlled boundaries remain distinct from real browser, connector, workload and account-limit acceptance.

No hosted CI is required for these checks. Native Windows/macOS behavior and browser-backed campaign cells require their own evidence; Linux fixture results do not establish them.

## Workload inputs and progress evidence

Workload version two includes deterministic PDF, DOCX and XLSX references from level two, plus a visual PNG code from level three. Their answers are checked separately from the reconciliation JSON. Inputs remain immutable, and the same generator applies to every effort. Format-reader checks establish usable fixtures; model interpretation still needs live evidence.

`oracle.ts` executes the generated reusable project against a new dataset through the installed native `codex sandbox --permission-profile :read-only`. The independent validation input and subprocess evidence belong in the campaign capture. The native home is separate from the task's home; the oracle verifies source integrity and bounds execution and output. Its controlled test demonstrates denied writes and network access on Linux.

`progress.ts` measures conservative intervals between distinct, retained reasoning, generation or tool-output observations. A phase change, explicit pause or gap over thirty seconds breaks continuity. Queueing, approval waits, backoff, final waiting and observation restarts earn no time. Only independently validated batches contribute accepted progress, and their interval records must be persisted before the queue total is checkpointed. This is an observational lower bound; elapsed process runtime alone cannot satisfy level five.

`capture-lane.ts` now timestamps native exec and app-server frames at receipt, before the production worker acknowledges their content. A bounded asynchronous lane lets later frames drain while it persists earlier ones; prompt capture still completes before native submission. Buffered frames share a receipt time, repeated native deltas cannot earn or bridge progress even when their transport envelopes are renumbered, and a saturated or failed capture leaves the cell uncertain. Finite live batches persist observed segments with zero level-five credit. A sustained coordinator must still bind those segments to each independently accepted batch and complete diagnostic export before checkpointing any two-hour total.

`evidence.ts` connects the runner to the dedicated workspace's production diagnostic worker. Required content must receive a durable attachment or complete-document acknowledgement. Admission checks collection health and reserves scope headroom; the runner must finish and rotate scopes before their limits. After all producers settle, exports include every trace bound to the campaign in the shared store, including events preceding binding and traces owned by runtime, child and title producers. Earlier campaigns retain their own failure records and bundles. Exports include explicitly scoped content and a bundle hash. An incomplete export cannot establish acceptance. The wrapper must never attach to a production diagnostic store.

Browser captures retain the visible conversation viewport without scrolling the page or waiting for animated layout stability. Visible credential controls, dialogs and embedded frames block capture; hidden embedding elements are inspected for visibility without reading their frame content or URLs. Before authenticated conversation readiness, excluded surfaces at page acquisition and navigation checkpoints are recorded as not applicable. Later missing conversation captures remain explicit omissions and prevent acceptance. Capture failures identify their stage, and exclusions identify a fixed reason without exposing field values.

`runner.ts` owns the continuous scheduling loop. A kernel-identified scheduler claim fences configuration changes and admission from competing runners. It drains serial cells before the concurrent lane, keeps at most two cell executors active, and switches protocol only between settled batches. The separate production admission layer also counts child and title generations. Observed account resets suspend admission in cancellable waits. A crashed or uncertain attempt stays running in the durable queue and requires reconciliation before another scheduler continues; a dead process alone is insufficient evidence for replay. Scenario executors must finish owned process/browser cleanup and retain failure evidence before returning an outcome.

Live synthetic top-level native submissions reserve starts at least three minutes apart in the campaign queue, including preparation, compaction, continuation, exec, and TUI turns. Reservations survive runner restarts; cancellation and a newly observed account hold stop a waiting submission. This reduces bursts but does not claim a provider quota or reset time. The launcher still enforces the separate maximum of two active non-Pro generations, including child work. Offline fixtures have no pacing delay.

Standalone live batches require the same initialized campaign queue. A typed failed native rate-limit terminal persists an admission hold before diagnostic capture and export. A local admission checkpoint retains the typed code and native identities; full terminal content remains in the production scoped transport capture. A checkpoint write failure remains an error and still attempts to persist the hold; its evidence path can therefore be unavailable and cannot establish acceptance. The hold fences later admission without settling concurrent or uncertain claims. Resumption requires a review of the retained observation, the current hold identity and owned attempts; a provider message without an exact reset does not establish a reset timestamp.

`live-batch.ts` owns one full runtime and native home for a serial task or concurrent pair. Each cell has its own disposable repository, native thread and capture trace. Artifact write permission is supplied per native task, so sharing a native home cannot redirect another task's Git permission. `native-scenarios.ts` owns native execution; independent project validation, committed-byte checks and production diagnostic queries remain outside the model's task. The batch returns only after native producers and runtime cleanup settle and the evidence scope is exported. `live-tool-probe.ts` uses this same owner for a single ordinary boundary.

`live-campaign.ts` maps completed batch evidence to exact queue claims. A complete export with an explicit `generationAdmitted=false` and no native cell result settles an evidenced pre-generation failure as failed; this does not authorize retry. Missing terminal evidence after admission, incomplete exports, mismatched cells, or shared native identities preserve the claims for reconciliation. A completed native task with invalid artifacts is a failed cell. The implemented automatic executors currently cover fresh, formats, Unicode, native image attachment, recoverable tool failure, large tool result, large-history, retained-conversation change, continued, resumed, archived-history, model-switch, Plan/revision/execution, Plan-stream interruption, TUI Plan/execution, and non-image reasoning/generation/tool steering and stop/continue cells at levels one through four. Unicode requires an exact committed UTF-8 artifact; the `tool-image` variant submits the generated PNG through native `--image` and requires its exact attached hash plus independently interpreted output; large-history requires a runner-owned fact from a long preparation turn to survive into a resumed turn without repeating that fact in the continuation prompt. Continued work uses two settled turns in one native app-server task. Model-switch work prepares on a different inspected non-Pro route, then performs the workload on the cell’s requested route in the same task. Both requested routes and their observed controls are bound to separate native turn IDs; a task-wide mixture of selections cannot establish the switch. The cell’s requested route is the continuation target, and the preparatory route is retained explicitly. Resumed work requires a completed preparatory exec turn, closes its process, then resumes the exact captured native task in a new process. Archived-history work additionally archives the completed preparatory task, observes its exact UUID in archived history, restores that same UUID, confirms removal from the archive, and closes the control process before resuming exec. A failed or missing preparatory terminal or an unconfirmed archive/restore transition prevents the second submission. Acceptance requires all expected browser selections and the matching native turn history. Other coordinators, including sustained level five, remain pending in the full matrix; executor availability is never an applicability exclusion or a pass.

The exact one-cell command inspects the current launcher session before claiming a durable cell, so a known sign-out does not consume an attempt. The batch owner inspects again after its owned launcher restart because the earlier observation cannot establish the later session state.

The `tool-failure` executor adds one runner-owned shell fixture that exits 17 with a fixed marker. The native task must run that exact command once, observe its returned nonzero tool result, then recover and commit the normal workload artifacts without changing the fixture. Acceptance uses the native command event, its exit code and marker, the unchanged input artifact, independent output validation and production tool receipts; model prose alone cannot prove the failure or recovery. A missing or repeated expected command makes the completed cell fail with its retained export.

The `large-tool-result` executor adds a runner-owned Bun script that emits 512 dataset-bound records and a final marker, about 39 KB of stdout. The native task must return the complete local command result once with enough output budget and commit its SHA-256 digest alongside the normal workload artifacts. Acceptance checks the exact completed native command output, one invocation, unchanged fixture, independently computed digest artifact, model selection and returned tool receipts. A truncated or repeated command result fails the completed cell; prose and a digest alone do not establish delivery. An isolated synthetic provider verified that the installed native Codex CLI returned all 39,449 bytes through the local tool boundary before this coordinator was enabled.

The `retained-conversation-change` executor prepares a task and an out-of-repository fact in one completed native turn, then resumes the exact task with a changed instruction. The second prompt omits the earlier fact but requires its committed witness and a separate revision artifact. Production diagnostics must show the first turn creating and retaining one launcher tab and the second turn reusing that same tab under its own native trace and browser-turn identity. Missing, foreign, duplicated or out-of-order lifecycle events prevent acceptance even if the model's artifacts are correct. This executor currently applies to Sol's retained local-tools path; Luna uses rolling checkpoints, so its declared cells remain pending until an applicable coordinator exists. No completed offline fixture is credited as a live ChatGPT pass.

If inspection reports `chatgpt_authentication_required`, open the owned hidden viewer with `just golden-viewer-open /absolute/path/to/workspace` and sign in inside that launcher. Keep PINs, QR codes, passkeys and cookies out of the terminal and diagnostic export. A previously submitted or evidence-blocked cell remains settled as recorded; after sign-in, select a distinct pending cell rather than replaying it.

Queue schema two retains each attempt's implementation identity and latest checkpoint. Migration from schema one preserves existing cell states, outcomes and unresolved claims. An active scheduler prevents migration. An implementation review cannot reset unresolved attempts or run alongside a live scheduler; stale queue instances cannot admit work after a revision. Only accepted passed coverage is requeued by a reviewed source revision. Failed, blocked and substituted attempts retain their outcome; changing source alone never schedules their replay. A blocked attempt requires an explicit review bound to its exact cell, attempt and outcome hash. A failed pre-generation attempt additionally requires the exact checkpoint hash and rejects any recorded native process or turn identity before it can be retried.

To inspect one specific finite serial non-Pro cell without an evaluated Bun command, run `bun scripts/golden/one-cell.ts CAMPAIGN_ROOT NATIVE_EXECUTABLE SOURCE_HOME CELL_ID`. This file-backed runner verifies the owned launcher, exact implementation and deployed helper, inactive borrowed tunnel, queue admission and cell identity before claiming work. It settles only a complete matching result; any producer or export uncertainty leaves the exact claim for reconciliation. An idle launcher restart retries only the typed `launcher_busy` refusal made before shutdown effects; other control failures retain their HTTP status and safe refusal code for review.

`reconcile.ts` applies an explicit implementation review without model work. The review JSON contains `expectedImplementationSha256`, `implementationSha256`, `reason` and a nonempty `verification` array describing the review evidence. It checks the current source and deployed artifact digest, retains both implementation manifests and the exact review bytes, and then atomically requeues every settled attempted cell. Earlier outcomes, checkpoints and implementation identities remain in attempt history; no earlier pass automatically becomes coverage for changed code. Staged files alone do not indicate that the queue changed. Capability changes still require separate applicability reconciliation.

```sh
bun scripts/golden/reconcile.ts context/golden/live /absolute/path/to/native/codex context/golden/implementation-review.json
```


`campaign.ts` connects that executor to the durable queue. Startup inspects the actual isolated session and native catalog. `implementation.ts` hashes executable source, including uncommitted files, and the selected native, Bun and browser-helper artifacts. The scheduler checks this identity before admission and after each batch; changes require evidence reconciliation. Checkpoints retain the scope, artifact directory, trace and native process/thread identity. Settled failures stop further admission for investigation. The optional fifth command-line argument bounds an observation by settled cells; omitting it keeps scheduling available cells until the lane settles, cancellation, backoff or a failure requires attention.

```sh
launcher/build/runtime/runtime/bun scripts/golden/campaign.ts \
  context/golden/live /usr/lib/chatgpt/resources/codex /path/to/existing/runtime-home
```

## Sign-in handoff

Starting `scripts/golden/workspace.ts` prints an “Open test sign-in” URL and a direct viewer URL. The local handoff page provides a keyboard-accessible button and instructions for the one-time sign-in. `--json` returns the corresponding machine-readable fields. The viewer assets live inside the private workspace, and the handoff URL contains the viewer's unguessable capability; keep that URL local to the user and task.

To revisit an active hidden launcher, run `just golden-viewer-open context/golden/live-reconciled-20260924` or `just golden-viewer-url context/golden/live-reconciled-20260924` to print its private browser URL. Replace the directory with your own workspace path. The command checks the display, viewer, and launcher process identities plus the viewer token before opening or printing the URL. In the DEV launcher's Settings, **Open hidden desktop** performs the same check and opens the browser; select the workspace folder if it cannot find one. In noVNC, press **Connect** if prompted. The hidden desktop is a separate display, so its launcher window does not appear among normal desktop windows. Keep the URL out of issues, logs, and exports, and do not capture authentication screens.

Present the sign-in URL to the user when authentication is needed. Wait for the user to finish before inspecting the session, and exclude authentication screens and credential entry from capture. `restartGoldenLauncher` preserves the isolated browser partition, uses the launcher's idle-only shutdown interface, and verifies process identity before replacing the launcher. Recovery of a stopped launcher requires its recorded leader and entire process group to be absent, an owned live display, and no conflicting descriptor owner; a surviving helper or reused PID prevents recovery. Descriptor readiness does not imply that its startup session refresh has finished.

ChatGPT sign-in and a full-mode MCP connection are separate prerequisites. Live tool workloads need a test tunnel and connector reaching their own broker. A browser-only Plan probe can verify the native Plan boundary while that setup is pending; it cannot substitute for tool or workload acceptance.

`runtime-config.ts` prepares full-mode configuration through the production config and tunnel contracts. It requires a canonical isolated home and matching campaign identity, and assigns a workspace-specific tunnel alias. A dedicated connector is optional: `borrowed-tunnel.ts` supports an explicitly selected existing connector and runtime-key file when the source configuration matches and its Responses port, broker and matching local tunnel aliases are inactive. Unknown ownership blocks admission. MCP commands explicitly select the isolated home and its broker socket. Preparation does not start a tunnel or any OS service; the runtime owner must bind its loopback port before saving configuration and observe tunnel readiness before admitting a tool workload. Native test homes share one explicit loopback provider configuration with account authentication and transport retries disabled.

`runtime.ts` owns service-free startup and cleanup in a dedicated runner process. It requires the owned live launcher, rejects an existing or ambiguously observed tunnel, awaits the production broker, persists the bound port and waits for tunnel readiness. The production launcher's MCP diagnostics discovery and probe must then observe healthy transport before scenario execution begins. The scenario callback owns settlement of its native producers. Runtime cleanup closes HTTP admission, browser workers, the dedicated tunnel and broker; cleanup errors retain the primary failure and prevent both successful completion and another runtime in the same process. Its controlled lifecycle test uses a synthetic tunnel executable and a loopback diagnostics server, so it does not establish live tunnel acceptance.

Startup and cleanup steps use the production diagnostic spans, including tunnel connection, readiness and local MCP inspection. A startup failure before the native callback retains its structured problem even when the batch contains no cell outcomes; the campaign must not replace that cause with a cell-identity mismatch. Tunnel discovery and control processes retain deadlines, process identity, observed exit code/signal, output-drain status, byte counts, truncation and termination evidence without copying raw command output into normal diagnostics. The runtime's profile locator follows the same production CLI contract as the launcher.

The runtime and its native producers must use the same canonical native home under the isolated workspace. Follow-ups may carry only historical environment XML, requiring the bridge to authenticate the exact current native rollout. The runtime owner scopes `CODEX_HOME` to that home, removes inherited SQLite-home overrides, and restores both environment values after cleanup. Concurrent producers in one runtime therefore share its selected native home while retaining separate task directories and native thread identities.

Successful runtime cleanup restores the isolated profile's previous configuration after checking that the runner's written content is unchanged. This prevents a later launcher restart from reconnecting a stale test runtime. Concurrent external writes require reconciliation; this check is not an OS-level compare-and-swap. Production configuration is read without reading or exposing the runtime-key contents. Borrowing a stopped tunnel for ordinary tests does not authorize disruptive tests against an active production runtime.

`live-tool-probe.ts` exercises one ordinary level-one tool boundary through the selected existing tunnel. It rotates a finished evidence scope, restarts only the owned isolated launcher, runs a native task against generated disposable inputs and checks its tool events, artifacts, commit and diagnostic bundle. This probe does not stand in for the full campaign matrix. Session inspection joins a pending saved-session refresh and propagates its failure before acquiring browser ownership.

After producers settle, probes persist their outcome before attempting export. If the original evidence transport fails, `finishGoldenEvidence` closes that client and uses the production worker to export the existing scope. Recovery requires its previously bound trace, records a collection omission for an unfinished scope, and always returns an incomplete result. It cannot admit a new model task or turn an uncertain outcome into success. If recovery also fails, both errors are retained and the durable outcome remains available for reconciliation.

Native test environments select the supplied Bun/native executable directories and system tools, with a disposable home and non-login shells. This keeps personal executable interceptors and login scripts out of artifact execution. The native configuration uses the documented [`allow_login_shell` and shell environment settings](https://learn.chatgpt.com/docs/config-file/config-reference). Full live profiles install the canonical production Interrupt hook against the isolated runtime home, and Compatibility V1 profiles use the production feature installer. Loopback-only provider fixtures can omit runtime integration. An installed-native fixture verifies authenticated exact-turn hook delivery without a ChatGPT request. Artifact-producing tasks receive write permission for their canonical disposable `.git` directory in addition to the workspace; Plan-only probes do not need that permission. The real native consumer fixture verifies a tool invocation, system Git selection, an artifact commit and a clean worktree without calling a model provider.

`structured-scenarios.ts` observes native phase events before applying steering or interruption, checks exact task and turn identity, and requires terminal settlement before a subsequent turn. Plan revision additionally requires a changed completed Plan item. Queued phases require correlated production browser-admission observations. Steering adds an independently checkable artifact requirement; a successful steering acknowledgement alone does not establish that the correction took effect.

The ordinary tool probe also accepts `plan-revise-execute` as its fifth command-line argument. It uses the same full runtime for two completed, distinct Plan items and the subsequent artifact-producing turn. `observations.ts` traverses the production query cursor for the exact capture scope and validates the correlated browser model-selection records against the requested route. These records describe confirmed browser controls, not unseen provider internals. The reader associates each native task with its production HTTP identity records before selecting browser events, rejecting traces claimed by multiple native tasks. Missing, mismatched or insufficient selection evidence fails acceptance.

Acceptance also checks that broker tool records belong to browser tasks selected on the same native trace. Each observed invocation must have one start and one definitive returned receipt; duplicate, cancelled or missing receipts fail. This establishes the instrumented invocation/receipt contract, not the absence of arbitrary uninstrumented external effects. Artifact commits are checked against the baseline ancestry, clean worktree and actual committed bytes, so ignored or assume-unchanged output cannot satisfy commit acceptance merely by appearing clean.

The interim diagnostic query excludes only its own still-running acceptance observer. That observer remains in the final exported scope, which is checked after it has settled. Retained evidence may be reconciled after an acceptance-reader defect is repaired; the original result and bundle remain intact, and no model turn is replayed on the strength of that repair.

Tool-outcome acceptance distinguishes returned receipts from intentional termination. A cancelled invocation is expected only when its production termination marker agrees with a completed native steering or interruption scenario, and its HTTP trace has one exact matching native task/turn owner. Generic aborts, timeouts, foreign owners and ambiguous trace ownership fail acceptance. Steering requires independent browser selection evidence for the predecessor and replacement, plus the committed correction artifact. An incomplete content bundle still prevents overall acceptance even when these individual checks pass.

The native scenario coordinator retains failed terminal records. Structured native `rateLimitExceeded` evidence can constrain account admission directly. Exec failures retain their actual task, terminal, process exit and preparation/execution phase without inventing a native turn ID or provider code. For every owned native task, batch finalization also queries the production diagnostic scope for an actual `chatgpt-http` conversation POST with HTTP 429, typed `rate_limit_exceeded`, and one unambiguous matching native task/turn identity. This check still runs after capture, oracle or cleanup failures. A dismissible ChatGPT request-frequency dialog is a `chatgpt-ui` notice, not an account limit; text that resembles a rate limit has no scheduling authority. `live-campaign.ts` can preserve an observed provider constraint even when the same bundle is incomplete; it does not settle or replay the affected claims. The queue persists an admission hold independently from observed-time backoff. A hold without a reset timestamp never expires by guessed elapsed time. Both the scheduler and standalone batch entry point reject new admission while it exists. Resumption uses the exact hold identity plus a retained review reason and evidence, with the scheduler stopped and uncertain attempts resolved; it leaves prior observation and review records available.

Before live admission, the golden implementation boundary builds the browser helper through the canonical build script into a disposable directory and compares its bytes to the launcher's advertised artifact. Knowing both source and artifact hashes alone is insufficient: a source launcher can advertise an older `.launcher-runtime/browser-helper.cjs` even after the packaged runtime build passes. A mismatch fails before browser acquisition or native generation. Rebuild the source helper with `bun run scripts/build-browser-helper.ts`, then reconcile any changed campaign implementation. The batch records the accepted helper digest in its diagnostic operation.

`admission-probe.ts` rechecks model controls and Send readiness under an existing account hold. It uses the owned hidden launcher and the production helper, prepares one synthetic draft, and rejects the required Send acknowledgement before the helper can activate the button. It accepts only that exact cancellation after draft release, complete diagnostic capture and the requested observed model/effort. Helper cleanup errors, unexpected completion, another abort, a missing release, or any submission/output signal leave readiness unproved. This is evidence that the previously failing UI boundary is available; it does not measure generation allowance or establish workload acceptance. The probe retains its own bounded bundle and never clears the queue hold itself. A successful probe can support an autonomous resumption review under the user's existing campaign authorization; it does not require a new user approval.

```sh
bun scripts/golden/admission-probe.ts context/golden/live chatgpt-web/light <exact-admission-hold-id>
```

Golden admission uses the production campaign's durable collection boundary. It requires a supported worker, available collection, no notices, no new reported drops since scope start, and complete retained capture. Historical drops remain visible in the lifetime counter and earlier bundles. Missing legacy boundaries cannot admit a new cell; rotate only after the earlier producers and outcomes have been reconciled. Completion flushes settled producers and exports the closed scope through the ordinary report pipeline, whose sequence and binding checks prevent an unrelated zero-loss interval from concealing selected evidence loss. Unreported loss and unknown native outcomes remain separate acceptance failures.
